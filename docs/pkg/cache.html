01 / DATA

cache

Read through a store, run the loader once per key however many callers arrive, and write the answer back with a jittered lifetime. An absent value is not cached.

INTERFACE

struct Cache[V]

structA cache in front of a store: take answers from the store when the value is there, and otherwise runs the loader once — not once per waiting caller — and writes the answer back with a lifetime that is jittered so a fleet warmed at the same moment does not expire together. A value is stored as bytes: the cache is over the codec, so it works for a record read out of SQL and for a counter read out of redis alike.

fn[V] Cache::new( store : &Store, encode~ : (V) -> Bytes, decode~ : (Bytes) -> V? raise, ttl_ms~ : Int64 = 60_000L, jitter? : (Int64) -> Int64) -> Cache[V]

itemA cache over store, reading and writing V through encode and decode, and keeping a loader's answer for ttl_ms milliseconds. jitter spreads an expiry over a window; the default answers a value between a tenth below and a tenth above the lifetime, which is what keeps a fleet from stampeding the database one second at a time.

fn[V] Cache::ttl_ms(self : Cache[V]) -> Int64

itemThe configured lifetime.

async fn[V] Cache::take( self : Cache[V], key : String, load : async () -> V?) -> V?

itemThe value under key, loading and caching it when the store does not have it. One loader runs per key however many callers arrive while it is working, and all of them receive its answer. None from the loader is not cached: an absent row may appear a moment later, and caching the absence is how a cache turns a transient gap into a minute of wrong answers.

async fn[V] Cache::evict(self : Cache[V], key : String) -> Unit

itemDrop key from the store, so the next take loads it again.

fn[V] Cache::inflight(self : Cache[V]) -> Int32

itemHow many loads are in flight, which is also how many keys are being shared.
